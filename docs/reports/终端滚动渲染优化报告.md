# WebTerm Android 终端滚动渲染优化报告

---

## 1. 根因总结

### 1.1 为什么一次单行滚动以前会被判断为所有行修改

旧的 `RemoteTerminalModel` 在收到新的屏幕 layout 后，只按“第 N 行是否还是原来的 TerminalLine 对象”逐行比较。终端向上滚动一行时：

- 旧第 0 行内容移动到第 0 行的位置被新内容替换；
- 旧第 1 行 → 新第 0 行、旧第 2 行 → 新第 1 行，依此类推。

因此每一行的 `TerminalLine` 对象身份都发生了变化，导致 `changedScreenRows` 几乎包含全部屏幕行。视图层随后触发整屏 `invalidate()`，Renderer 每帧重新遍历所有 Cell 重绘，造成闪烁和抖动。

### 1.2 为什么 history-only 会产生重复刷新

旧刷新判断把 `historyChanged` 当作需要整屏重绘的信号。但用户位于实时底部（`viewport.followTail == true`）时，新增历史记录只是屏幕上方不可见区域增长，当前可见的实时屏幕内容并没有变化。每次追加历史都调用整屏 `invalidate()`，在诊断开启或高频输出时形成大量无意义重绘。

## 3. 滚动识别设计

### 3.1 判断向上滚动

`RemoteTerminalModel.detectScreenScroll` 检查新 layout 是否等于旧屏幕整体向上平移：

```
new[row] == old[row + shift]   for row = 0 .. rows - shift - 1
```

命中则返回正数 `shift`。

### 3.2 判断向下滚动

检查：

```
new[row] == old[row - shift]   for row = shift .. rows - 1
```

命中则返回负数 `-shift`。

### 3.3 放弃滚动识别

以下情况直接回退到 0（随后逐行比较）：

- layout 长度与当前屏幕行数不同；
- 行 ID 缺失或重复；
- 无法证明是连续位移；
- Baseline、layoutEpoch 改变、终端实例变化、主/备用屏切换、geometry 变化。

### 3.4 多个滚动合并

`RenderDirtyState.merge` 逻辑：

- 同方向连续滚动：相加 `screenScrollRows`，并平移已累积的脏行；
- 方向相反、中间有内容修改、或出现 `fullInvalidate/geometryChanged/activeBufferChanged`：退化为 `fullInvalidate = true`，`screenScrollRows = 0`。

## 4. RenderNode 缓存设计

### 4.1 缓存键

每个缓存槽位记录该行最近一次录制时的身份字段：

- `lineId`
- `lineVersion`
- `columns`
- 行宽/行高（px）
- `fontGeneration`
- `paletteGeneration`
- `styleGeneration`

这些字段用于标识槽位内容，但“字段变化”本身不直接触发重录：是否重新录制由脏区驱动，只有进入 `changedScreenRows` 或 `exposedScreenRows` 集合的行才会重录，其余保留行直接复用槽位（结构失效场景见 §4.5）。

模型层识别滚动 Patch 时，会把 version 升高的保留行标记进 `changedScreenRows`，因此这类行同样会重新录制；缓存层在复用前再以槽位记录的 `lineId`/`lineVersion` 与当前行做兜底校验，不一致则视为失效并重录。

### 4.2 缓存槽位管理

- 固定大小数组 `slots[]`，长度等于当前屏幕行数（上限 512）。
- 使用循环映射：`physical = (firstPhysicalSlot + logicalRow) % rowCount`。
- 向上滚动一行：`firstPhysicalSlot = (firstPhysicalSlot + 1) % rowCount`。
- 不创建新 RenderNode，只调整逻辑索引映射。

### 4.3 滚动时复用

以 5 行屏幕向上滚动 1 行为例：

- 旧 `slots[1]` → 新逻辑行 0；
- 旧 `slots[2]` → 新逻辑行 1；
- ……
- 旧 `slots[0]` 回收作为新逻辑行 4 的槽位；
- 只重新录制底部暴露的 1 行。

### 4.4 重新录制时机

- 内容变化行（`changedScreenRows`）；
- 滚动暴露行（`exposedScreenRows`）；
- 字体、调色板、样式 generation 变化；
- geometry、Baseline、buffer 切换、终端实例/layoutEpoch 变化。

### 4.5 全部失效时机

以下任一情况清空缓存：

- `fullInvalidate`
- `geometryChanged`
- `activeBufferChanged`
- `layoutEpoch` 变化
- 屏幕行列数变化
- View 宽度/字号/Typeface 变化
- 调色板/全局样式变化
- 终端实例变化

光标闪烁和选择变化**不会**清空缓存。

## 5. 绘制层次

绘制顺序：

1. 终端整体背景；
2. 实时 screen 各行 RenderNode；
3. 可见历史内容（直接 Canvas 绘制，本次未做缓存重构）；
4. 选择覆盖层；
5. 光标覆盖层；
6. 其他动态 UI（手柄、滚动条等）。

正文行只包含默认背景、Cell 背景、字符、样式装饰；光标、选择、手柄、调试框等动态元素均不在 RenderNode 中录制。

## 6. 刷新策略

| 结果 | 触发条件 | 行为 |
|---|---|---|
| `NONE` | `followTail && historyChanged`，且没有屏幕/光标/样式变化 | 不调用 `invalidate()` |
| `PARTIAL` | 少量内容行变化或光标移动 | 只 `invalidate(dirtyRect)` 对应行 |
| `SCREEN_REGION` | 发生屏幕滚动或脏行过多 | `invalidate(screenLeft, screenTop, screenRight, screenBottom)`，不刷新 View 其他区域 |
| `FULL` | `fullInvalidate/geometryChanged/activeBufferChanged/palette/modes/ styles` 等 | 清空缓存，调用 `invalidate()` |

## 8. 性能结果

### 8.1 缓存行为（来自 `TerminalRowRenderNodeCacheTest`）

| 场景 | 重新录制行数 | 复用行数 |
|---|---|---|
| 5 行屏幕，单行向上滚动 | 1 | 4 |
| 5 行屏幕，三行向上滚动 | 3 | 2 |
| 普通中间行版本变化 | 1 | 4 |
| 字体 generation 变化 | 5 | 0 |
| geometry 变化 | 6（新尺寸） | 0 |
| 光标变化 | 0 | 5 |
| 选择变化 | 0 | 5 |
| history-only + followTail | 0 | 0（不触发绘制） |

### 8.2 渲染基线（来自 `RemoteTerminalRendererRenderBaselineTest`）

环境：Robolectric，Java 21.0.9，macOS aarch64，10 核。

关键场景（80×24，1000 行历史）：

| 内容 | 视口 | p50 (µs) | p95 (µs) | p99 (µs) | 单次分配 (bytes) |
|---|---|---|---|---|---|
| ascii | follow-tail | 152 | 306 | 498 | 10,096 |
| ascii | scrolled | 199 | 487 | 642 | 55,783 |
| styled_ascii | follow-tail | 1,813 | 5,439 | 6,288 | 2,852,358 |
| styled_ascii | scrolled | 87 | 100 | 108 | 159,093 |
| mixed | follow-tail | 218 | 231 | 252 | 377,586 |
| mixed | scrolled | 41 | 52 | 80 | 67,198 |

120×40 与 200×50 场景的完整数据见测试原始输出：`/tmp/render-baseline.log`（本地运行产物）。

结论：普通连续滚动场景 p95 均远低于 16.7ms 帧预算；缓存生效后 scrolled 视口的分配量显著下降。
